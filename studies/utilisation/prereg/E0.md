# E0 preregistration · 2026-11-16

Status: owner authorised execution after prior documentation is complete;
remaining scoring/calibration decisions are explicit below.
Scope: two model variants on 164 HumanEval+ tasks, three generations per arm,
one seed per sample, 1968 scheduled responses. Pilot requests and previous
HumanEval study responses are excluded.

## Question and competing predictions

Do P1 and P3_1 produce different mean single-generation test-suite success on
the same tasks? An example-guided strategy might improve success or stabilise
formatting; it might instead distract a small model or add cost with no useful
change. Both instruction wording and the example differ, so the estimand is
the complete strategy comparison. This design does not isolate examples.

Primary outcome is, for each model, mean over 164 tasks of
[mean(P3_1 passes over 3 seeds) - mean(P1 passes over 3 seeds)].
Each task has equal weight. Generalisation concerns these two fixed variants,
one public benchmark and this host. Benchmark exposure in training is unknown.
A pass means satisfying the specified tests, not proof of general correctness.

## Exact prompt materials

System text: "You are a helpful coding assistant."

P1 instruction: "Complete the Python function. Return only code."
P3_1 instruction: "Complete the Python function following the example."

P3_1 demonstration task:
    def lookup_status(statuses, key):
        """Look up key; return unknown if absent."""

Demonstration solution:
    def lookup_status(statuses, key):
        return statuses.get(key, "unknown")

The builder joins instruction, any example and target with two LF characters
and appends one LF. Example template:
    Example task:
    {example_prompt}
    Example solution:
    ```python
    {example_solution}
    ```
The actual backticks have no escaping. Target template is "Task:\n{task_prompt}"
with the benchmark prompt stripped of trailing whitespace.
Canonical implementation is src/prompt_energy/prompts.py and config literals
in experiments/config.py. Hash both with the rendered stimulus manifest.
P3_1 uses one original study-authored example. Before generation audit its
text and semantics against all 164 benchmark tasks, record results and flag
potential overlap. No assertion of completed semantic audit is made here.

## Outcomes and failure rules

Save raw HTTP envelopes and response fields before evaluation. Run evaluation
in separate time blocks with the approved Windows Job, AST policy, minimal
environment, temporary directory, 256 MiB limit and 60-second candidate budget.
Score both base and plus partitions. Last complete python/py/unlabelled fenced
block defining the required function is selected; otherwise use stripped text.
Prepend the original task prelude. Preserve extraction and runtime outcomes.

Input count mismatch, transport errors and unparseable API responses are
invalid attempts. Preserve and report each; any rerun has a distinct attempt
ID and retains the same task/arm/sample identity and settings. No selecting
among answers by correctness. If an attempt is irrecoverably invalid, report
the missing cell and task-level coverage. The primary paired estimate then
uses tasks with all six valid responses per model, with the missingness
pattern disclosed; no imputation or denominator substitution.

Valid input with empty output, no required function, syntax error, sandbox
policy rejection, failed tests, runtime error, timeout, memory limit or output
cap contributes a non-pass under the registered constrained-runtime outcome.
Record each type separately. Evaluator infrastructure errors are missing
scores and require inspection, never an automatic model failure.
The 2048 cap is censoring, not evidence of refusal or intent.
An output extraction defect must be reported before any scoring-rule change;
any rescore is versioned and marked with the prior outcome retained.

## Analysis

Print scheduled, attempted, valid-input, scored and paired-complete counts,
by model and arm. Show seed-level pass flags for every task.
Use 2000 task-bootstrap resamples, seed 1732, paired arms and all three seeds
retained within task. Report the 2.5th and 97.5th percentiles for primary
paired differences. For inferential p-values, use exact paired task sign-flip
randomisation (swap the complete arm triplets within task) for the two-sided
absolute mean-difference statistic. Compute exactly by dynamic programming on
integer pass-count differences; no normal approximation. Holm correct the
two model-level primary p-values. Report unadjusted and corrected values.
These are benchmark-level randomisation summaries with their exchangeability
assumption stated, not a random sample of all possible programming problems.

Secondary descriptive reports: each arm's mean success, any-of-three success
and a task-ID 2×2 table based on any-of-three success. Sample-index discordance
tables are separate diagnostics and do not treat 492 responses as independent
tasks. Cost outcomes are tokens, wall time, API prefill and decode durations,
and the supporting energy totals under EXECUTION.md. Include all scored
failures in cost numerators; label coverage and censoring. Avoid an umbrella
"utilisation gap" number combining incompatible outcomes.

## Interpretation checks

Before interpreting a difference, inspect extraction failures, differential
invalid-input counts, output-cap rates, policy rejections and whether a few
tasks dominate the paired differences. An interval permitting differences in
both directions weakens an arm-ordering interpretation. A result sensitive
to missing-score or policy patterns motivates a qualified report and an
independent replication. These are checks and competing explanations,
not criteria for dropping tasks or deciding which result to publish.
